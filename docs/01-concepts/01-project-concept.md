# プロジェクトコンセプト：Webアクセシビリティ評価ポータル

作成日：2026年9月13日  
プロジェクト：a11y-portal  
サービス仮称：Webアクセシビリティ観測室

本書は、企画紹介とFチームの共同開発計画を統合したコンセプト文書です。資料に記載された企画案を整理したものであり、実装済みの機能や確定した評価結果を示すものではありません。対象サイト・技術構成・担当は今後決定します。

## 1. コンセプト

**日本のWebサイトについて、利用者が操作で困る箇所と改善方法を日本語で共有し、修正と再確認につなげる公開ポータルをつくる。**

「評価を見つける → 困りごとを理解する → 直す → 確かめる」という流れを支えます。対象ページで目的の操作を完了できるかを確認し、その条件・結果・改善案を、サイトを作る人や運営する人が行動に移せる形で残します。

AI対応への関心をきっかけに、障害のある人が使いやすいWebサイトを増やすことを目指します。

## 2. 背景と解決したい課題

企画の出発点は、情報アクセシビリティ勉強会で、障害のある人がWebサイトを使う際の困りごとを知ったことです。情報が掲載されていても、ボタンの用途が分からない、メニューを開けない、入力エラーに気づけないといった理由で、目的の操作を完了できない場合があります。

改善に着手するには、問題の存在だけでなく、誰が・どの環境で・どの操作をしたときに困るのか、何を直し、どう確かめるのかが伝わる必要があります。本プロジェクトでは、操作結果、再現手順、確認環境、改善例を一つのレポートにつなげます。

なお、勉強会で聞いた経験や資料中の一般例は、個別サイトの検査結果として扱いません。

## 3. 対象者と提供価値

| 対象者 | 提供する価値 |
| --- | --- |
| Webサイトの制作者・開発者 | 問題を再現し、改善案を実装し、同じ操作で修正を確認できる |
| Webサイトの運営者 | 利用者への影響と確認範囲を理解し、修正や補足・訂正に着手できる |
| 障害のある利用者・評価に協力する人 | 操作上の困りごとを具体的な記録として共有し、改善後の結果を確認できる |
| 共同開発に参加するメンバー | 実際の成果物を通じて、評価・実装・レビュー・公開の流れを経験できる |

## 4. 大切にする考え方

### 4.1. 利用者の目的と操作を中心にする

「メニューを開いて目的のページへ進む」「検索する」など、利用者が達成したいことを評価の単位にします。単一の点数や順位よりも、何が起き、どのような利用者に影響し、どう改善できるかを伝えます。

### 4.2. 確認した範囲と限界を明示する

対象URL、確認日時、環境、操作手順を記録し、未確認のページ・操作・環境を明示します。初期版は対象ページと操作に限った確認結果として公開し、サイト全体の適合判定に広げません。サンプルは実測結果と区別します。

### 4.3. 自動検査と人による操作確認を組み合わせる

WCAGを参照して関連する要件を整理し、自動検査とVoiceOver・キーボードによる操作確認を組み合わせます。自動検査の結果、実際の操作結果、再評価の状態は分けて表示します。自動検査で問題が検出されないことだけで、すべての人が使えるとは判断しません。

### 4.4. 改善と再評価につなげる

問題の指摘とともに、修正のヒントや改善例を示します。初期版から訂正連絡先を用意し、将来は運営者による補足・訂正や修正後の再評価を継続して反映できる形を目指します。

### 4.5. AI対応の可能性は仮説として検証する

見出し、リンクの名前、ボタンの役割など、意味が伝わる構造を整えることは、人とAIの双方のWeb利用に役立つ可能性があります。AI対応への関心をアクセシビリティ改善の動機につなげることが、本企画の仮説です。

AIの操作成功が、障害のある人の使いやすさを保証するわけではありません。人とAIの評価は別々に確認し、AIによる操作結果との比較は将来の検証対象とします。

## 5. 基本の利用体験

1. **評価を見つける**：一覧でサイト名、対象ページ・確認操作の範囲、評価の状態を確認し、詳細へ進む。
2. **困りごとを理解する**：目的の操作、再現手順、実際の結果、利用者への影響、確認環境を読む。
3. **改善方法を知る**：改善案や関連する基準、確認に使うツールを参照し、修正に取り組む。
4. **修正後に確かめる**：同じ手順で再確認し、結果を更新する。履歴の蓄積は段階的に拡張する。

企画資料の画面モックには、検索・カテゴリによる絞り込み・並べ替えなども描かれていますが、初期版の必須範囲には含めません。モック内のサイト名・件数・日付・評価は架空のサンプルです。

## 6. 初期版でつくるもの

**対象1サイト・1ページについて、一覧から1件の評価詳細と改善案を読める状態を公開すること**を最小の到達点とします。

| 項目 | 初期版の範囲 |
| --- | --- |
| 一覧画面 | サイト名、確認範囲、状態を表示し、評価詳細へ移動できる |
| 詳細画面 | 対象ページの操作手順、確認結果、環境、改善案、未確認の範囲を表示する |
| 評価データ | 手動で整理したデータをリポジトリ内のファイルで共有する |
| 訂正の導線 | 補足や訂正を届けられる連絡先を掲載する |
| 公開成果物 | GitHub上のコードと、別のPCから閲覧できる公開URLを用意する |
| ポータル自身の操作確認 | キーボードとVoiceOverで主要な導線を操作できることを確かめる |

初期版ではブラウザ内だけに評価データを保存せず、公開先でも同じ内容を読めるようにします。実測が間に合わない場合はサンプルであることを明記し、公開できた範囲と未対応事項を共有します。

### 評価レポートに残す情報

以下は両資料をもとに整理した記録項目です。具体的なデータ形式は実装前にチームで決めます。

| 情報 | 記録内容 |
| --- | --- |
| 識別と対象 | レポートID、サイト名、対象URL、確認したページ・操作の範囲 |
| 確認日時・環境 | 確認日時、OS・ブラウザ・支援技術とそのバージョン |
| 操作と結果 | 達成したいこと、再現手順、期待する結果、実際の結果、利用者への影響 |
| 評価方法 | 自動検査と手動確認の区別、使用ツール、関連するWCAGの要件 |
| 改善 | 修正のヒント、改善例、修正後の確認方法 |
| 状態と限界 | 未確認の範囲、実測・サンプルの区別、再評価の実施状況 |
| 訂正・更新 | 訂正連絡先。更新・再評価の履歴は将来の拡張対象 |

## 7. 初期版の完成条件

- 別のPCから公開URLを開ける。
- 一覧から1件の詳細へ進み、操作結果と改善案を読める。
- 対象URL・確認日時・環境・操作と、未確認の範囲を確認できる。
- サンプルを使っている場合は、その旨を明確に表示している。
- 補足・訂正の連絡先が掲載されている。
- キーボードとVoiceOverで主要な導線を操作できる。
- GitHubのコード、公開URL、短いデモ、未対応事項を共有できる。

## 8. 共同開発の進め方

2026年9月13日のワークショップでは、13:05〜16:00の約3時間で初期版を公開し、全員がブランチ・PR・レビューの流れを体験する計画です。最初の公開は13:40を目安とし、後半に操作確認と修正の時間を確保します。

- 最初に完成条件、対象ページ、共通データの形、担当ファイルを決める。
- 土台・統合・公開、一覧画面、詳細画面、評価・データを分担し、人数に応じて兼任やペア作業にする。
- 小さな変更をPRにし、作業者以外がレビューしてから統合する。評価データも同じ流れで共有する。
- 共通CSSや設定の変更は担当者間で調整し、統合後は公開先でも確認する。
- AIには共通の完成条件と担当ファイルの範囲を伝え、行き詰まったら早めにチームで相談する。
- 15:30以降は機能追加を止め、完成確認と発表準備に集中する。

詳細な時間配分・分担案は[共同開発計画](./03-f-team-workshop-plan.pdf)を参照してください。

## 9. 将来の拡張と未決定事項

### 将来の拡張

- URL入力による自動検査、自動巡回。
- 対象サイト・ページ・確認操作の追加。
- 改善例、確認ツール集、再評価・訂正履歴の充実。
- 投稿フォームやデータベースを使った継続的な情報管理。
- AIの操作結果と、人による操作確認の比較・検証。

### 実装前に決めること

- 評価対象のサイト・ページと、確認する操作。
- 技術構成、起動方法、公開先、公開担当。
- 共通データの形式と担当ファイルの境界。
- VoiceOverを使える端末と確認担当。
- 訂正連絡先と、補足・訂正を反映する運用。

既存の検査ツールを活用する方針で、資料にはWAVE・AccessMonitorや、実装用エンジン候補のaxe-coreが挙げられています。採用ツールは未決定です。

## 11. ドキュメントの配置・命名規則

`docs`配下のディレクトリとファイルは、同じ階層内で順序が決まるように、2桁の連番とハイフンを先頭に付けます。今後追加する文書や資料もこの規則に従います。

```text
docs/
└── 01-concepts/
    ├── 01-project-concept.md
    ├── 02-web-accessibility-portal.pdf
    └── 03-f-team-workshop-plan.pdf
```

読む順序は、プロジェクトコンセプト、元の企画紹介、共同開発計画とします。改名や移動を行う場合は、参照リンクも併せて更新します。
