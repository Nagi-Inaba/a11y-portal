# a11y Portal UI設計ガイド（草案）

更新日：2026年9月13日

このガイドは、フロント担当と一覧・詳細の実装担当が、同じ見た目と操作ルールで作業するための設計案です。提出された画像生成用JSONの雰囲気を引き継ぎ、デジタル庁デザインシステム（以下DADS）の指針とアクセシビリティの確認方法を補っています。

最初の到達点は、共通のUIを使った「一覧から詳細を開き、操作結果と改善案を読んで戻れる」体験です。今回は設計資料を作成した段階で、画面の実装と実機確認は次の作業になります。

## 2. 引き継ぐデザイン

コンセプトは「落ち着いて読めて、改善の手掛かりが見つかる公開ノート」です。温かな白、墨色の本文、深いプラム、細い罫線を使い、サイト名・確認範囲・操作結果・改善案に視線を導きます。

ノートの立体感はヒーローの装飾に限定します。ノートの見出しと3項目はHTMLにし、紙の面と影はCSSで表現できます。本文と評価一覧は不透明な背景に置きます。モバイルでは装飾を小さくしても、固有の説明は読める形で残します。

ロゴの輪郭は既存画像の重なった円形マークを参考にします。独立したロゴ素材が用意されるまでは、テキストの「a11y Portal」で表示できます。

DADSはブランド色をリンクに使う場合も想定しています。今回はプラムを残し、下線とリンク名で操作を見分けられるようにします。フォーカスにはDADS指定の黒と黄色を使います。[リンクテキスト](https://design.digital.go.jp/dads/foundations/link-text/)、[カラー](https://design.digital.go.jp/dads/foundations/color/)

現在の実装はNext.js、React 19、TypeScript、通常のCSSです。まず公式文書とHTML例を必要な部品単位で参照し、この構成に合わせます。React版の例を直接転用する場合は、依存するスタイルとReact 19との互換性を確認します。

## 4. 色・文字・余白のルール

元JSONの主要な色の組み合わせを、sRGBの相対輝度から計算しました。以下は不透明な単色同士の比率です。スクリーンショットの実測や、実装後の全状態の検証結果ではありません。

| 用途 | 前景／背景 | コントラスト比 | 設計上の扱い |
| --- | --- | --- | --- |
| 本文／ページ | `#252724`／`#FAF9F6` | 14.30:1 | 維持 |
| 補足文字／ページ | `#5C5B55`／`#FAF9F6` | 6.47:1 | 維持。注記を薄くするための透明度を加えない |
| 白文字／主ボタン風リンク | `#FFFFFF`／`#62456D` | 8.10:1 | 維持 |
| プラム文字／淡いプラム背景 | `#62456D`／`#F2EDF4` | 7.02:1 | 維持 |
| セージの点数文字／背景 | `#285841`／`#EAF3ED` | 7.24:1 | 配色案として維持 |
| 小麦色の点数文字／背景 | `#754700`／`#FFF1D6` | 7.08:1 | 配色案として維持 |
| 操作に必要な枠／ページ | `#79756E`／`#FAF9F6` | 4.35:1 | 操作枠や意味を持つ区切りに使用 |
| 薄い罫線／ページ | `#DAD8D0`／`#FAF9F6` | 1.36:1 | 装飾に限定。操作の唯一の識別手段にしない |

通常の文字は4.5:1以上、操作の識別に必要な図形などは隣接色と3:1以上を基準にします。装飾だけの罫線を同じ条件で判断するものではありません。[文字のコントラスト](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html)、[非テキストのコントラスト](https://www.w3.org/WAI/WCAG22/Understanding/non-text-contrast.html)

元の18px本文、16px一覧、1.75の本文行間、1184pxの最大コンテンツ幅、余白の段階を初期案として保ちます。pxは標準設定での見た目の参考値とし、文字サイズは`rem`、行間は単位なしで実装します。サンプル注記・確認範囲・採点説明は16px相当以上にします。

48pxは独立した主操作の幅・高さの設計値です。WCAGの最低寸法が48pxという意味ではありません。文中リンクには一律の高さを与えず、対象の寸法と間隔、適用される例外を確認します。[ターゲットのサイズ](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html)

## 5. 一覧・詳細・点数の設計

一覧は最新の評価から最大5件を表示し、実装時の件数はデータから生成します。0件、1件、5件のすべてで成立させます。横長の並びは`ul`・`li`とCSS Gridで構成し、サイト名と値の関係をラベルで伝えます。比較・ランキング機能を導入する場合には、別途テーブルの必要性を検討します。

一覧と詳細は同じデータを参照し、`sample-001`ではサイト名・対象ページ・日付・82 / 100・サンプル表示をそろえます。PCとモバイルに別々の評価データやDOMを用意せず、同じ情報を並べ替えます。

5件のサンプルのうち、詳細の本文が提供されているのは`sample-001`です。最初の動作確認にはこの1件を使い、5件のデータは一覧の密度確認にも使います。ほかの項目に詳細へのリンクを付ける際は、対応する内容とルートを用意します。別の一覧ページがない段階では「すべての評価レポートを見る」は表示しません。

点数は残します。採点方法が未定の間、架空の点数を表示できるのはサンプルと明記したデータに限ります。実測の数値を出すには、方式・バージョン・対象・環境・日時と根拠が必要です。点数がなければ「未採点」と表示し、0点や検査エラーとは分けます。

サンプルのセージ・小麦色・プラムは、色分けの閾値を示していません。本番の初期案は、採点の色分けが決まるまで全件プラムにそろえる形です。点数をサイト全体の適合率や操作成功率と説明せず、自動検査・操作確認・再評価の状態を別に載せます。

点数のラベル・値・分母・サンプル属性は普通のHTMLテキストで読める形を基本にします。大きな数字と小さな分母に分けた際の実際の読み上げを確認し、分断が起きる場合に補助テキストを検討します。

詳細では対象、点数、主要な確認条件を上部に置き、操作結果・再現手順・改善案・再確認方法を見出しでたどれるようにします。改善案は最初から読める状態にします。`.example`のURLは架空の対象として文字で表示します。

## 6. 実装時のアクセシビリティ確認

`information-accessibility-practice`を設計・実装・確認に使用し、WCAG 2.2 A/AAを実装目標の案とします。画像や部品の採用だけで、ポータルが適合したとは扱いません。

| 段階 | 確認する内容 | 記録する証拠 |
| --- | --- | --- |
| 基礎UI | 見出し、リンク名、本文へ移動、フォーカス、色と状態 | HTML・アクセシビリティツリー、色計算、フォーカスの画面 |
| レイアウト | 320 CSS px幅、400%ズーム、文字だけの200%拡大、長い名称、余白設定の変更 | 幅・倍率・入力内容と、情報が切れないことの確認記録 |
| 一連の操作 | 一覧→詳細→改善案→一覧へ戻る | Tab・Shift+Tab・Enterの手順と結果 |
| 支援技術 | 見出しとリンクの移動、点数と注記、読み順 | VoiceOver/Safariの実機結果と各バージョン |
| 統合後 | 自動検査と訂正の導線 | 対象URL・日時・ツール・指摘・対応結果 |

拡大時はヒーローや一覧の高さを固定せず、縦に伸ばします。行間1.5倍、段落後2倍、字間0.12em、単語間0.16emへの変更も、言語に適用される条件で確認します。[リフロー](https://www.w3.org/WAI/WCAG22/Understanding/reflow.html)、[テキストのサイズ変更](https://www.w3.org/WAI/WCAG22/Understanding/resize-text.html)、[テキストの間隔](https://www.w3.org/WAI/WCAG22/Understanding/text-spacing.html)

WindowsのNVDAによる確認は補助に使えます。企画上の完成条件にあるVoiceOverの確認は、対応端末で別に行います。AIによる観測と人による実機確認は証拠として分け、自動検査で指摘がないことだけを完成条件にしません。

## 7. 次の作業と担当の境界

フロント担当は、ブランド、共通トークン、主要部品、レスポンシブのルールを持つ案です。`src/app/globals.css`と`src/app/layout.tsx`は共有部分なので、一覧・詳細の担当者と編集範囲を合わせます。JSONの`implementation_handoff`に対象ファイルの候補を記載しています。

次の作業は、この草案でsample-001の一覧・詳細をブラウザに表示し、見た目と主要な操作を確認することです。開始時にデータ担当と項目・型を合わせます。採点方式が未定でも「未採点」とサンプルで画面の確認を進められます。公開時には、使える訂正連絡先を設定します。

この草案では原文JSONと参照画像を確認しました。Node.jsでJSONを解析し、原文のバイト一致、サンプル5件・4画面・既存14色の保持、ローカル参照先を検証しています。単色の文字色21組が4.5:1以上、操作枠2組が3:1以上であることも計算で確認しました。実画面の操作確認、VoiceOver、DADSスニペットの互換性確認は実装時の作業です。
