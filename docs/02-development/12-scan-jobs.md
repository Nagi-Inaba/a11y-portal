# URL受付・自動検査・定期実行

登録済みURLを画面から受け付け、Webアプリとは別のワーカーでaxe-coreの検査を行います。成功時の結果から投稿の下書きを作成し、人による操作確認と管理者のレビューを経て公開できます。再試行やワーカー停止による期限切れも、試行履歴に残ります。

## 導入と実行

1. 既存SQLに続けて `supabase/migrations/20260914010000_scan_jobs.sql` を適用します。既存の公開レポート・投稿は保持されます。
2. Supabase Authに検査ワーカー専用アカウントを作成し、確認済みにします。そのUUIDをSQL管理者が `public.scan_workers(user_id)` に登録します。このアカウントを `report_admins` に登録したり、投稿者として共用したりしないでください。サービスロールキーは不要です。
3. 管理者が `/admin/scan-targets` から、検査してよい公開URL、追加接続先、確認目標を登録します。URLと接続先は実行履歴を維持するため変更できません。変更時は旧対象を停止し、新しい対象を登録します。
4. Node.js 22、`npm ci`で入れた依存関係、インストール済みのGoogle Chromeをワーカー実行環境に用意します。Chromeの実行ファイルを確認し、絶対パスを指定します。Windowsでは署名済みシステムChromeを使用します。Playwright同梱Chromiumのダウンロードは不要です。
5. **ワーカー専用**の環境変数に、次の値を設定します。秘密情報をWebアプリの環境やリポジトリへ入れないでください。

| 環境変数 | 内容 |
| --- | --- |
| `NEXT_PUBLIC_SUPABASE_URL` | 同じSupabaseプロジェクトのURL |
| `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` | 同プロジェクトの公開キー |
| `SCAN_WORKER_EMAIL`・`SCAN_WORKER_PASSWORD` | 専用アカウントの認証情報 |
| `PLAYWRIGHT_CHROMIUM_EXECUTABLE_PATH` | 確認済みChromeの絶対パス |

環境変数を設定済みなら `npm run scan:worker` で起動します。`.env.worker` に設定した場合は、次のようにNodeへ明示的に読み込ませます。同ファイルはGitの除外対象です。

```sh
node --env-file=.env.worker --experimental-strip-types scripts/scan-worker.mts
```

末尾に `--once` を付けると、期限が来た定期検査の受付と、待機中の1件の実行を行って終了します。通常起動では、1件ずつ処理し、処理間に5秒待って次を確認します。プロセス監視・再起動は配備先で設定します。WebのHTTPリクエスト内ではChromeを起動しません。

本番DBへの適用、ワーカーの配備、常駐プロセスの起動は、このローカル実装では実行していません。配備先・費用・実際の対象サイトは運用時に設定します。

## 投稿者と管理者の操作

投稿者は `/contribute/scans` でURLを入力します。受付後は状態、実行回数、試行ごとの開始・終了日時、失敗理由を確認できます。自分以外の投稿者の検査結果は読めません。管理者が設定した定期実行のジョブは、その設定を最初に登録した管理者の一覧に入ります。

成功した検査の「下書きとして投稿」から、既存の投稿画面へ進みます。自動検査結果は保持し、人の操作結果は未確認のままです。必要な操作・環境・連絡先を記入して提出し、管理者が公開します。ボタンを再度押しても同じ下書きへ戻ります。

対象に関連レポートがない場合は新規投稿です。最初の投稿が同じURLで承認されると、そのレポートが対象へ紐付き、次の検査は同じIDへの再評価投稿になります。既存レポートを指定するときも公開済みURLとの一致が必要です。投稿のURLを別サイトへ変更した場合は自動紐付けを行いません。

定期実行の間隔は60〜43200分で指定します。空欄で定期実行だけを止められます。対象を無効にすると新規受付と待機中の検査を停止します。すでに実行中の処理は終了まで通信する場合がありますが、無効化後の結果は成功として保存しません。

## 上限と失敗時の扱い

| 制御 | 現在の値・動作 |
| --- | --- |
| URL | 登録済みの完全一致。HTTP 80・HTTPS 443、認証情報なし、DNSホスト名 |
| 接続先 | 対象のオリジン＋追加9件まで。ワイルドカードなし |
| 受付間隔 | 対象ごとに5分以上。同じ対象の進行中ジョブは1件 |
| 投稿者の受付数 | 同時に待機・実行中の検査は3件まで |
| 再試行 | 初回を含め3回まで。失敗後は試行回数×60秒待機 |
| 実行時間 | 検査45秒、親プロセスの強制終了65秒、DBの実行期限90秒 |
| 通信 | 1実行256リクエスト・20MBまで。各ソケットの無通信期限15秒 |
| 保存容量 | 結果JSONは1MBまで。ブラウザ用Nodeプロセスのヒープ上限256MB |

接続制限・容量超過・通信量超過・対象停止は自動再試行を行いません。通信・検査の失敗と中断は上限内で再試行します。ワーカー停止で報告が失われた場合は、次回のジョブ取得処理が期限切れを検出します。ワーカーがすべて停止している間は進みません。

失敗時は結果を保存せず、「検査に失敗」と表示します。失敗を検出0件として扱いません。遮断された追加通信がある成功結果には件数と制限を記載します。対象の描画へ影響していないか、人の確認が必要です。

## 接続・権限・公開の境界

ブラウザごとのプロキシで、DNSのIPv4応答がすべて公開アドレスであることを確認し、そのIPへ直接接続します。ブラウザによる再解決に任せないため、接続直前にDNSの応答が変わっても内部IPへ接続しません。IPv6だけの対象には対応していません。除外するIPv4範囲は[IANAの特殊用途アドレス一覧](https://www.iana.org/assignments/iana-ipv4-special-registry)を参照しています。

HTTPのリダイレクトとHTTPSのCONNECTも同じ制限を通します。GET・HEADだけを許可し、Service Worker・WebSocket・QUIC・プロキシ外のWebRTC通信を制限します。Service Workerの通信は通常のrouteで捕捉できないため、[Playwrightの案内](https://playwright.dev/docs/api/class-browsercontext#browser-context-route)に従いブロックします。ログイン状態・DB資格情報をブラウザの子プロセスへ引き継ぎません。Chromeのサンドボックスを有効にし、各実行で新しいブラウザを作ります。

ワーカーは専用RPCでジョブを取得・完了報告します。投稿の作成・編集・公開や、ジョブテーブルへの直接更新は許可しません。実行中のジョブに対応するトークンと期限を照合し、古いワーカーの完了報告を拒否します。自動検査だけで人の操作を確認済みにすることもDBで拒否します。

対象・ジョブの状態変更と、対象へ紐付く投稿の承認は、共通のDBロックを最初に取得して順序を統一します。低頻度の検査を想定した構成です。規模を拡大する場合は、実測してロックと実行基盤を見直します。

配備先では、ワーカー専用ユーザー・ネットワーク制限・OSのメモリ上限と、Chromeの更新運用を設定してください。アプリ側の制限を、OS全体の隔離が検証済みという意味には扱っていません。

## 検証

本番ビルド後、確認済みChromeのパスを設定して実行します。

```sh
npm run test:scans
npm run test:scans:browser
npm run test:scans:worker
npm run test:scans:ui
```

API・DBのテストでは実際のマイグレーションをPGliteで実行し、AuthとPostgRESTだけをテスト用に置き換えます。受付制限、権限、試行履歴、期限切れ、定期受付、対象停止、手動確認の必須化、公開と再評価への紐付けを確認します。PGliteは単一接続なので、実PostgreSQLの複数接続での負荷・待ち時間は未検証です。

ブラウザ検査のテストは、DNS応答とソケットの接続先をテスト内だけで置き換え、ローカルの制御したページを実際のChrome・axeで検査します。内部IP、DNSの応答変更、混在応答、リダイレクト、追加通信、POST・WebSocketの遮断を確認します。本番ワーカーにはテスト用の切り替え設定はありません。

起動コマンドのテストでは、ワーカー認証から子プロセスの接続拒否とDBへの完了報告まで確認します。画面テストでは対象登録・上限件数の接続先の再保存・定期設定・受付・結果・下書き・失敗表示を操作し、1280pxと320pxでaxeを実行します。画像は `_work/scans-ui/` に保存します。実サービスのDB更新や第三者サイトの検査は行いません。

独立レビューの3件（無効化競合・workerの投稿権限・異なるURLへの紐付け）は修正し、限定再レビューで解消を確認しました。そこで追加指摘された承認時のロック順序は、承認RPCの入口で共通ロックを取得するよう修正し、権限・投稿・CMS・DBの回帰テストで確認しています。最終のロック修正に対する独立再レビューは行っていません。
